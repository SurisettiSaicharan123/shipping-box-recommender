The core design question
This is a 3D bin-packing problem, and how you handle it is probably what they're judging. A sensible approach is:

Filter out boxes whose weight capacity is below the order's total weight.
Check that every item fits the box on its own, trying rotations.
Use a simple packing heuristic, such as shelf or layer packing, or a volume check plus a per-item fit check as a fast first pass.
Pick the cheapest box that passes, and break ties by smallest volume.
State your simplifying assumptions in the README, and return a clear "no box fits" result.

Models

Product: name, length, width, height, weight
Box: name, inner length/width/height, max weight, cost
Order and OrderItem: product, quantity. You can skip these and accept items directly in the API request if you want to keep it small.

services/packing.py
This is the core. It takes plain dataclasses in and returns a result, with no database access:

select_box(items, boxes) -> Recommendation | None
helpers such as fits_weight, item_fits_box (with rotations) and pack_items
the result includes the chosen box, total weight, volume used and a reason string

Because it's pure Python, test_packing.py runs fast and needs no database.

API

POST /api/recommend-box/ takes {"items": [{"product_id": 1, "quantity": 2}]}
It returns the recommended box and the reasoning, or a clear "no box fits" response.

What's in it

Algorithm (boxes/services/packing.py): pure Python. Boxes are filtered by weight, then volume, then whether each item fits alone (with rotation). A guillotine packing check follows. The cheapest passing box wins, and ties go to the smaller volume.
Models: Product and Box, with validation and database check constraints, both editable in the admin.
API (POST /api/recommend-box/): it returns the box, an order summary and item placements. It returns clear errors for bad JSON, bad quantities, unknown products and orders that don't fit.
Tests: packing, models and API, including a randomized check that any packing the algorithm claims is in bounds with no overlaps.
CI: a GitHub Actions workflow runs the same tests on every push.
Docs: README.md covers the approach, assumptions and setup, and TEST_OUTPUT.md holds the real test run.
